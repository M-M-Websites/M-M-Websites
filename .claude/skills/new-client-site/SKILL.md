# New client site

## Shared rules (apply to every step)

1. **Nothing goes to clients or prospects without Michael's approval.** Write drafts only; Michael reviews and sends. Never send email, post, or submit forms on anyone's behalf.
2. **The only public email is `mnmwebsitesforyou@gmail.com`.** Never use or write `hello@mnmwebsitesforyou.com`.
3. **Pricing is $600 one-time setup + $45 a month maintenance.** Never quote anything else unless Michael says so.
4. **Payments are card, Apple Pay or Link only.** Never mention Cash App, Klarna, Amazon Pay, bank debit, PayPal or any other method.
5. **Stripe is fully set up. Don't touch it**: no new products, prices, payment links, portal or branding changes.
6. **One cold email per business, ever.** No follow-ups.
7. **No ownership promises.** Clients do not own the website, code, hosting or domain; if they stop paying, the site goes offline, the domain is paused and updates stop. They keep their own name, logo, photos and words. Never write "you own", "yours to keep", "in your name" or "hand it over", on the client's site or anywhere else.
8. **No invented facts**: no testimonials, reviews, client counts, years in business, stats, results, awards, prices, hours, addresses or phone numbers that the client hasn't confirmed in writing. Missing facts stay empty and hidden; never fill them with placeholders that look real.

## Steps

1. **Collect the brief before writing anything.** You need: business name, trade, city/service area, the client's own services and prices (if they publish prices), contact methods (phone, email, booking link, socials), photos they supplied, logo, and the one action visitors should take (call, book, request a quote). List anything missing and ask Michael; don't guess.
2. **Pick a slug and make the folder.** Use the business name in kebab case (e.g. `legendary-detailing`). Every client site lives in this repo at `clients/<slug>/`, self-contained: its own pages, assets, `_headers`, `tests/`, `wrangler.toml`, `worker.js`, `.assetsignore`, `CLAUDE.md` and `seo/`. Nothing in it may depend on files outside its folder, and nothing outside may depend on it. Don't create a separate GitHub repo.
3. **Start from the pattern, not from scratch.** Use `M-M-Websites/legendary-detailing` (client site) and the studio site at this repo's root as references for structure only. All paths below are inside `clients/<slug>/`. Copy the mechanics, never the content or the look:
   - `index.html`, `404.html` (root-relative asset paths), `robots.txt`, `sitemap.xml`, `.nojekyll`, `.gitignore`, `.assetsignore`
   - `assets/css/`, `assets/js/main.js`, self-hosted fonts in `assets/fonts/` with their `OFL.txt` (or other licence)
   - `scripts/set-domain.sh` (rewrites the canonical, Open Graph, JSON-LD, sitemap and robots URLs and writes `CNAME`)
   - `tests/package.json` and `tests/site.test.cjs`
   - `wrangler.toml` + `worker.js` (Cloudflare Worker with Static Assets, `not_found_handling = "404-page"`, `html_handling = "auto-trailing-slash"`). The Worker is named `<slug>`, `assets.directory = "./"` (the client folder, not the repo root), and the client's `.assetsignore` lists `tests`, `scripts`, `seo`, `*.md`, `wrangler.toml` and `worker.js` like the root one.
   - Tell Michael the one Cloudflare step he must do: create a Workers Build for the client connected to this repo with root directory `clients/<slug>` and a build watch path of `clients/<slug>/*`, then attach the client's domain. The studio site's root `.assetsignore` already lists `clients`, so client sites are never published under mnmwebsitesforyou.com.
4. **SEO groundwork, before writing any copy.** In `clients/<slug>/` (the client's SEO folder is `clients/<slug>/seo/`):
   - Run `hr-seo-project-setup` to make `clients/<slug>/seo/`, then `hr-seo-context` to write `seo/seo-context.md` from the brief (trade, towns served, services, the one action visitors should take, competitors Michael or the client named).
   - Run `hr-keyword-research` for the client's services and towns. A new site has no Search Console data yet, so the evidence is web search (what appears, People Also Ask, related searches) plus any Keyword Planner export Michael provides; volumes stay `unknown` otherwise. Save the shortlist in the client's `seo/keywords/`.
   - Run `hr-keyword-clustering` on the shortlist to map each cluster to a page or section, one primary keyword per page, and keep the map in `seo/`. Pages beyond the agreed site are Michael's call; list them as suggestions, don't build them.
   - Optional for a crowded trade: `hr-competitive-landscape` to see what the local leaders' pages cover.
   Use the client's real words and facts in all of it; the keyword map shapes headings and wording, it never adds claims the client hasn't confirmed.
5. **Create one owner settings file** (`assets/js/content.js` or `config.js`) holding contact details, socials, hours, reviews and the form email. Every value starts empty unless confirmed. Anything empty must be hidden on the page, and the form must say plainly that it isn't connected yet instead of pretending to send.
6. **Build the standard sections**, adapted to the trade: hero with one clear offer and CTA, services (with the client's real prices only if they gave them), work/gallery from their own photos, why choose them (from facts they gave), service area, booking or quote form, FAQ, footer. Reviews stay hidden until real ones exist, word for word.
7. **Give the client their own visual identity.** Don't reuse M&M's paper/ink/red or Legendary's black/gold. One signature element, deliberate type, restrained motion, `prefers-reduced-motion` respected, and the page works with JavaScript off.
8. **SEO basics, from the keyword map:** unique title and description per page built on its primary keyword, exactly one H1 naming the service and city, logical H2/H3s that answer the questions found in step 4, absolute canonical (placeholder domain until `set-domain.sh` runs), Open Graph tags and image.
   - **Structured data with `hr-schema-markup`:** `LocalBusiness`-type JSON-LD (the most specific subtype for the trade) with only confirmed fields (no address if they come to the customer), plus `FAQPage` only if the FAQ is visible word for word. No `aggregateRating` or `review` unless real reviews are shown on the page. Validate it and record the result; anything not checked is "pending", not passed.
   - **AI-search basics (from `hr-ai-search-visibility`):** each service section opens with a plain answer (what it is, who it's for, the area served, the price if the client publishes one); facts stated plainly enough to quote. `robots.txt` must not block GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot or Google-Extended, and ask Michael to confirm Cloudflare's AI-crawler blocking is off for the client's zone.
9. **Security headers in `_headers`:** `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, HSTS, caching rules for `assets/*`, and a strict CSP with no `unsafe-inline` or `unsafe-eval`. Allow only the hosts the site really uses (e.g. `formsubmit.co`, `static.cloudflareinsights.com`). If there is an inline `no-js`→`js` script, put its `sha256-` hash in `script-src`.
10. **Write the test suite** covering: layout at 320/390/768/1024/1440/1920px with no horizontal overflow, no console errors or failed requests, tap targets ≥ 44px, in-page and internal links, form validation plus success and failure with FormSubmit mocked (never send real email), the unconnected-form state, axe-core with zero violations (light and dark if the site has a dark theme), JS-off and reduced-motion fallbacks, the exact CSP from `_headers`, the 404 page, `set-domain.sh`, and a content check that fails on invented or placeholder text.
11. **Take the client's own wording rules into the repo:** add a `CLAUDE.md` with their confirmed facts, prices and anything they don't want said, plus a line that SEO work uses the repo's `hr-*` skills, reads `clients/<slug>/seo/seo-context.md` first, and keeps its files in that unpublished `seo/` folder.
12. **Hit the Lighthouse target:** Accessibility, Best Practices and SEO = 100 on mobile and desktop; Performance as high as practical (aim ≥ 90 mobile). Use responsive WebP images with width/height, preload the main font, lazy-load below-the-fold images.
13. **Pre-launch SEO check.** Run `hr-seo-audit` on the local build (crawl, titles, canonicals, sitemap, robots, Lighthouse) and fix what it finds. Then run `hr-google-business-profile` to draft the profile setup for the client: primary and secondary categories, services, description and the landing page, as ready-to-paste text for Michael to pass on (part of launch help; never edit the profile yourself).
14. **Ship it with the `ship-site` skill.** Once Michael has the client's domain, run `bash scripts/set-domain.sh <domain>` before the first live push. After it's live, onboard the domain to Search Console, GA4 and IndexNow with `svk-onboard-site` (needs Google access, see `svk-setup-google-access`) and submit the sitemap once Michael confirms.
15. **Book the first real SEO check.** Add one dated follow-up to `seo/README.md`'s Follow-ups list for 28 days after launch: run `hr-seo-audit` and `hr-local-seo` against real Search Console and GA4 data, then `hr-keyword-research` from the striking-distance queries. Offer once to make it a scheduled task; Michael confirms.
16. **Report back to Michael:** what was built, test and Lighthouse results, the SEO files in `seo/` (keyword map, schema check, audit, Business Profile draft) and the check-back date, every empty setting the client still needs to supply, and a draft handover message for Michael to review and send. Don't send it.
